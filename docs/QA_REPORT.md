## 2. Vulnerabilities Discovered & Remediated

Every issue identified during the adversarial code review was fixed directly in `src/` while strictly preserving Hexagonal Architecture boundaries (`src/domain` and `src/application` remain 100% free of `grammy`, `better-sqlite3`, `pino`, or HTTP adapter imports).

### 2.1 Delivery Guarantees, Multi-Admin Fanout & Partial Batch Failure Atomicity

| ID | Component | Vulnerability Found | Production Impact | Remediation Implemented |
| :--- | :--- | :--- | :--- | :--- |
| **REL-01** | `TweetMonitorService` & `TelegramAlertNotifier` | Previously, any error thrown by `AlertNotifier.sendTweetAlert()` lacked retryability classification, and `TelegramAlertNotifier` did not fallback if Telegram rejected HTML entity edge cases with HTTP `400`. | Transient Telegram `502`/`503`/network outages could either drop alerts if marked seen early or stall other alerts in the cycle; conversely, a permanent `400`/`403` across all configured admin chats would infinitely retry every poll cycle forever. | Introduced typed `AlertDeliveryError({ retryable: boolean })` and `isNonRetryableDeliveryError()` in `src/application/ports/alert-notifier.ts`. Multi-admin fanout in `TelegramAlertNotifier.broadcastHtml()` isolates per-chat errors (one blocked/kicked admin chat never blocks remaining valid admin chats), automatically retries HTTP `400` entity errors once as stripped plain text, and marks total failure `retryable: true` iff at least one chat failed transiently (`>=500`, `429`, or network error) when zero chats succeeded. `TweetMonitorService` marks `seen_tweets` **only after** delivery succeeds (or when all admin chats fail with non-retryable `4xx` errors). |
| **REL-02** | `TweetMonitorService` | Multi-batch query loops (>20 handles) had no per-batch `try/catch`; if Batch 2 threw a `503` or timeout, the entire `runOnce()` aborted before delivering Batch 1's collected tweets, OR naive continuation would advance `last_tweet_poll_unix` past Batch 2's failed window. | Either healthy batch alerts were delayed/blocked by a single failing chunk, or advancing `last_tweet_poll_unix` on partial failure permanently skipped tweets in the failed chunk beyond `overlapBufferSeconds`. | Isolated each search batch in its own `try/catch` inside `TweetMonitorService.runOnce()`: healthy batches still deliver and mark `seen_tweets`, while `last_tweet_poll_unix` is **held back** whenever `cycleErrors.length > 0` (unless aborted). On the next cycle, Batch 1 tweets are skipped in O(1) via `seen_tweets` while Batch 2's missed window is recovered cleanly. |
| **REL-03** | `TweetMonitorService` | Pagination relied solely on `page.hasNextPage && page.nextCursor !== null && pagesFetched < maxPagesPerBatch`. If upstream returned the **same** `next_cursor` twice, an empty `tweets: []` page with `has_next_page: true`, or pages containing 100% duplicate tweet IDs, the loop kept burning paid API credits up to `maxPagesPerBatch`. | Wasted API credits and `5.5s` pacing slots per stuck cursor on every 60s poll cycle. | Added a `seenCursors = new Set<string>()` loop detector plus a `newTweetsOnPage === 0` early-exit guard in `TweetMonitorService.runOnce()` that logs a structured warning and terminates pagination immediately. |
| **REL-04** | `TweetMonitorService` | After prolonged downtime or when tracking hyper-active accounts, hundreds of unseen tweets inside the lookback window could burst into Telegram in a single cycle. | Outbound Telegram rate-limit storms and operator alert fatigue. | Added `maxAlertsPerCycle` (default `50`) flood-cap protection in `TweetMonitorService`. When exceeded, tweets are prioritized so **all `HIGH`-relevance NFT alerts** (contract addresses, mint links, trigger keywords) survive while lowest-priority overflow tweets are marked seen and suppressed. |
| **REL-05** | `ProfileMonitorService` | Single `try/catch` wrapped the entire user batch loop, and `updateProfileSnapshot()` could overwrite baseline fields if `sendProfileAlert()` failed transiently. | One failed chunk aborted subsequent chunks; transient Telegram outage during a bio/website swap would overwrite the baseline and permanently lose the `"было → стало"` diff. | Enforced `Math.min(batchSize, 100)` chunk cap, isolated per-chunk errors, and wrapped `sendProfileAlert()` so retryable delivery errors preserve the prior SQLite profile snapshot for automatic re-diffing on the next cycle. |

### 2.2 Rate Limiter, Timeouts, `Retry-After` Parsing & Shutdown Under Load

| ID | Component | Vulnerability Found | Production Impact | Remediation Implemented |
| :--- | :--- | :--- | :--- | :--- |
| **NET-01** | `RateLimitedHttpClient` | Pending request queues (`highQueue`, `normalQueue`) were unbounded, and queued items did not listen to `AbortSignal` until popped by `drainQueue()`. | Hours of hung/slow upstream responses could accumulate unbounded closures in RAM; `SIGINT`/`SIGTERM` or cancelled `/add` commands could leave aborted items sitting in queues. | Added `maxQueueSize` (default `100`) rejecting overflow fast, plus immediate `AbortSignal` event listeners on queued items that splice them out of `highQueue`/`normalQueue` and reject immediately on abort. |
| **NET-02** | `RateLimitedHttpClient` | `await response.text()` executed **outside** the `try/catch` block of `fetch()`, and `finally { cleanup() }` detached the caller's `AbortSignal` before reading the response body! | If TCP headers arrived in 100ms (HTTP 200) and the response body stream hung mid-chunk, `cleanup()` had already unhooked the abort signal and `response.text()` errors bypassed retry logic. | Moved `await response.text()` **inside** the `try` block while `combinedSignal` (`AbortSignal.timeout(timeoutMs)` + caller `AbortSignal`) remains active, so mid-body socket hangs time out deterministically and retry on transient failures. |
| **NET-03** | `RateLimitedHttpClient` | `parseRetryAfterMs()` called `Number.parseFloat(trimmed)` before `Date.parse(trimmed)`. Because `parseFloat("2026-11-08T14:30:15Z")` returns `2026`, ISO-8601 date strings were misinterpreted as `2026 seconds` (`33.7 minutes`!), and `TwitterProviderRateLimitError.retryAfterMs` on final 429 exhaustion was uncapped (`Retry-After: 999999` -> `999,999,000ms`). | Bogus or ISO-formatted `Retry-After` headers could stall retry windows or report multi-day delays. | Restricted delta-seconds parsing to strict `/^\d+(?:\.\d+)?$/` before falling back to `Date.parse()` (supporting RFC-1123 and ISO-8601 dates), and clamped `retryAfterMs` on `TwitterProviderRateLimitError` to `maxBackoffMs`. |
| **NET-04** | `RateLimitedHttpClient` | In `notifyAuthOrQuotaError()`, `lastQuotaAlertAtMs` was updated **before** `await onAuthOrQuotaError(...)` succeeded. | If Telegram had a 2-second blip at the exact moment `TwitterAPI.io` credits ran out (`402`), the admin credit-exhaustion alert was suppressed for a full 30 minutes. | Updated `lastQuotaAlertAtMs` to the full 30-minute cooldown only on delivery success, applying a 60-second retry cooldown if the alert callback throws. |
| **NET-05** | `PayloadNormalizer` & `TwitterApiIoProvider` | `readIdString(raw, ['id', 'id_str', ...])` checked `'id'` first regardless of type (corrupting 64-bit X Snowflake IDs `> 2^53 - 1` when JSON contained both numeric `id` and exact `id_str`), omitted `'rest_id'` on tweet `author` objects, ignored numeric `createdAt` values, and did not chunk `getUsersByIds()` inside `TwitterApiIoProvider`. | Precision loss on 64-bit tweet/user IDs broke URL links and deduplication keys; >100 user IDs in `TwitterApiIoProvider.getUsersByIds()` could exceed upstream batch limits. | Updated `readIdString()` to prefer non-empty string values across **all** candidate keys (`id_str`, `rest_id`, string `id`) before falling back to finite numbers, added `'rest_id'` to tweet/referenced-tweet author ID extraction, supported numeric `createdAt`, validated `http(s)://` on tweet URLs, and chunked `TwitterApiIoProvider.getUsersByIds()` at `MAX_BATCH_USER_IDS = 100`. |

### 2.3 SQLite Multi-Week Durability & Handle Rename Collisions

| ID | Component | Vulnerability Found | Production Impact | Remediation Implemented |
| :--- | :--- | :--- | :--- | :--- |
| **DB-01** | `migrations.ts` & `SqliteAccountRepository` | `tracked_accounts` had a non-unique index on `handle`, while enforcing naive `UNIQUE(handle)` directly would throw `SQLITE_CONSTRAINT_UNIQUE` whenever Account A (`id=111`) renamed to `@foo` while paused/suspended Account B (`id=222`) still held `@foo` in SQLite (or when two accounts swapped handles simultaneously). | Either duplicate handle rows caused `/remove @foo` ambiguity, or handle swaps crashed the entire `ProfileMonitorService` batch transaction with `SQLITE_CONSTRAINT_UNIQUE`. | Added Migration `2` (`002_unique_account_handle`) healing any pre-existing duplicate handles and creating `UNIQUE INDEX idx_tracked_accounts_handle_unique ON tracked_accounts(handle COLLATE NOCASE)`. Wrapped `upsertNewAccount()` and `updateProfileSnapshot()` in SQLite transactions calling `displaceConflictingHandles()`, which atomically renames any stale conflicting row (`user_id != current`) to `${baseHandle}#${user_id}`. Updated `SearchQueryBuilder` to filter out non-standard handle placeholders (`/^[a-z0-9_]{1,15}$/`) and `AccountManagementService.addAccounts()` to skip the local cache fast-path when an existing handle belongs to a paused or unavailable row so recycled handles resolve fresh `userId`s from X. |
| **DB-02** | `SqliteDatabase` & `env.ts` | Continuous writes under `PRAGMA journal_mode = WAL` without periodic `wal_checkpoint(TRUNCATE)` can leave `.db-wal` files enlarged under steady reader concurrency; operators also commonly configure `DATABASE_PATH` as an alias for `SQLITE_DB_PATH`. | Gradual `.db-wal` disk growth; misconfigured env path fallback. | Verified `fs.mkdirSync(dir, { recursive: true })`, `WAL` mode, `busy_timeout = 5000`, and `idx_seen_tweets_seen_at` (`SEARCH seen_tweets USING INDEX idx_seen_tweets_seen_at`), added `PRAGMA wal_checkpoint(TRUNCATE)` inside `SqliteDatabase.optimize()` (invoked hourly by `MaintenanceService`), and supported `DATABASE_PATH` fallback in `loadAppConfig()`. |
| **DB-03** | `MockTwitterProvider` | When `MOCK_AUTO_EVENTS=true`, synthetic tweets and users were inserted into `tweetsById` and `usersById` `Map`s every cycle without eviction. | Unbounded heap growth in long-running staging/mock deployments. | Bounded `tweetsById` (`<= 500`) and `usersById` (`<= 1,000`, preserving seeded profiles) with FIFO eviction. |

### 2.4 Telegram Formatting, Unicode Surrogates, URL Schemes, Callback Limits & Polling Supervision

| ID | Component | Vulnerability Found | Production Impact | Remediation Implemented |
| :--- | :--- | :--- | :--- | :--- |
| **TG-01** | `html-escape.ts` & `TelegramFormatter` | **Critical**: `TelegramFormatter` interpolated `account.websiteUrl`, `avatarUrl`, `bannerUrl`, `tweet.url`, and change diffs into `<a href="...">` with only HTML entity escaping. Telegram's HTML parser **strictly rejects** non-HTTP protocols (`ipfs://...`, `javascript:...`, `ethereum:...`, `data:...`, bare ENS domains `vitalik.eth`) with `400 Bad Request: Unsupported URL protocol`! | Any tracked NFT founder putting `vitalik.eth` or `ipfs://...` in their X website field caused **every** profile/tweet alert referencing that URL to fail with HTTP `400`! | Added `sanitizeTelegramHttpUrl()` and `renderSafeHtmlLink()` in `src/infrastructure/telegram/html-escape.ts` allowing **only** `http:` and `https:` URLs with valid hostnames (`<= 2048` UTF-8 bytes) and rendering unsafe/schemeless URLs as escaped `<code>...</code>` text instead of `<a href>`. Applied across all 10 `<a href>` sites in `TelegramFormatter`. |
| **TG-02** | `html-escape.ts` & `TelegramFormatter` | `clampText()` sliced strings by UTF-16 code units (`value.slice(...)`), splitting surrogate pairs (`🔥`, `🚀`, mathematical bold symbols) into lone surrogates (`\uD83D`) and potentially exceeding Telegram's `4096` UTF-16 limit when HTML tags/entities expanded (`&` -> `&amp;`) or when `/keywords` had hundreds of triggers. | Invalid UTF-8 lone surrogates or `> 4096` char payloads trigger `400 Bad Request` (`message is too long` / `can't parse entities`). | Implemented `toWellFormedUnicode()` (replacing lone high/low surrogates with `U+FFFD`), `Intl.Segmenter` grapheme-safe + UTF-16 code-unit `clampPlainText()` (never splitting surrogate pairs or ZWJ emoji sequences), `ensureMaxTelegramHtmlLength()` (`<= 4096` fallback), `NaN` timestamp guards, and `/keywords` list display clamping (`<= 80` inline keywords + summary count). |
| **TG-03** | `TelegramBotAdapter` | Needed hard guarantee that inline `callback_data` never exceeds Telegram's `64`-byte UTF-8 limit even if X returns unusual/corrupted `userId` strings, without leaking memory. | `400 Bad Request: BUTTON_DATA_INVALID` if any button exceeds 64 UTF-8 bytes. | Verified all prefix formats (`tgl_rep:`, `tgl_en:`, `rm_ask:`, `rm_yes:`, `rm_no:`, `ls_p:`, `chk_now`) are `12–29` bytes for standard Snowflake IDs, and added `safeCallbackData()` with a bounded (`<= 256` FIFO entries) compact `~token` lookup map guaranteeing `Buffer.byteLength(data, 'utf8') <= 64` for arbitrary inputs. |
| **TG-04** | `TelegramBotAdapter`, `retry-transformer.ts`, `bootstrap.ts` & `index.ts` | 1) `TelegramBotAdapter.startPolling()` assigned `this.bot.start(...)` without `.catch()` — `bot.catch` only catches middleware errors, **not** `bot.init()` (`getMe`) or `getUpdates` `409 Conflict` rejections! 2) `grammY` defaulted `client.timeoutSeconds` to `500s` (8.3 min). 3) `retry-transformer.ts` only retried `429`, not `502`/`503`/`ECONNRESET`. 4) `bootstrap.ts` awaited `telegramBot.stopPolling()` sequentially before `coordinator.stop()` without `try/catch` (`bot.stop()` makes an outbound `getUpdates` call that throws when offline, skipping `coordinator.stop()` before `sqliteDb.close()`!). | Transient Telegram `502` or deploy-overlap `409 Conflict` could kill inbound bot polling permanently or crash Node via `unhandledRejection`; offline `SIGTERM` could skip coordinator stop or hang for minutes. | 1) Replaced bare `bot.start()` with `runPollingSupervisor()` loop with exponential backoff + jitter (`1s..60s`) waking immediately via `AbortSignal`. 2) Set `client: { timeoutSeconds: 45 }`. 3) Extended `createTelegramRetryTransformer()` to retry `429`, `5xx`, and transient network errors (excluding long-polled `getUpdates`). 4) Propagated lifecycle `AbortSignal` into `/add` and `chk_now` handlers. 5) Hardened `bootstrap.ts` shutdown with `Promise.allSettled([stopPolling(), coordinator.stop()])` bounded by an `8s` `Promise.race` timeout, plus a `12s` `.unref()` failsafe exit timer in `src/index.ts`. |

## 4. Real Daemon Smoke Execution (`dist/index.js`)

Executed compiled `dist/index.js` in a child Node v22.12.0 process with:
- `MOCK_MODE=true`, `MOCK_AUTO_EVENTS=true`
- `SQLITE_DB_PATH=<tmpdir>/deep/nested/monitor.db` (non-existent nested parent directories)
- Unreachable/unauthorized dummy `TELEGRAM_BOT_TOKEN` to exercise live polling failure supervision

### Observed Results
1. **Startup & Persistence**: Recursively created `<tmpdir>/deep/nested/`, initialized SQLite in `journal_mode = wal`, applied `schema_migrations` versions `1` and `2` (`idx_seen_tweets_seen_at`, `idx_tracked_accounts_enabled`, `idx_tracked_accounts_handle_unique`), seeded 12 default NFT trigger keywords, and ran initial database maintenance.
2. **Polling Supervision**: Caught `401: Unauthorized` from `getMe` inside `TelegramBotAdapter.runPollingSupervisor()`, logged a structured JSON event (`backoffMs: 60000`), and kept `MonitorCoordinator` alive with zero unhandled rejections.
3. **Graceful `SIGTERM` Shutdown**: Upon `SIGTERM` while mid-sleep inside both `MonitorCoordinator` (`15s` sleep) and `TelegramBotAdapter` (`60s` backoff), `AbortController` woke all timers immediately, stopped background loops and SQLite cleanly, and exited with code `0` in **`39ms`**.
